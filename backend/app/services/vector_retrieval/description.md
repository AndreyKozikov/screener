В нашем пайплайне векторная обработка реализована по принципу Sentence-level Embedding (эмбеддинги на уровне предложений). Это более продвинутый подход, чем просто векторизация всего куска текста целиком.

Вот пошаговый процесс:

1. Разбиение на чанки (Chunking)
Сначала документ разбивается на крупные блоки (чанки) по заголовкам или по размеру (около 3000 символов). Это позволяет сохранить контекст (например, всю таблицу или формулу целиком).

2. Разбиение чанка на предложения (Sentence Splitting)
Каждый чанк перед векторизацией разбивается на отдельные предложения (используется регулярное выражение в EmbeddingService).

3. Векторизация (Embedding)
Запросы: Каждый поисковый запрос (например, "формула купона") превращается в один вектор.
Чанки: Для каждого чанка мы получаем массив векторов — по одному вектору на каждое предложение внутри этого чанка.
4. Поиск (Retrieval по методу MaxSim)
Это ключевой момент. Когда мы ищем соответствие между запросом и чанком:

Мы сравниваем вектор запроса с вектором каждого предложения внутри чанка.
Вычисляем косинусное сходство.
Для этого чанка берется максимальное сходство среди всех его предложений.
Почему так? Если в чанке на 3000 знаков есть одно предложение, которое идеально отвечает на вопрос, то весь чанк получит высокий балл, даже если остальной текст в нем — "вода".
5. Агрегация баллов
Если у нас 5 поисковых запросов по умолчанию, то итоговый балл чанка — это сумма его "лучших попаданий" по каждому из 5 запросов.

6. Ранжирование и MMR
После того как мы нашли топ-30 самых релевантных чанков:

Мы вычисляем средний вектор чанка (центроиду всех его предложений).
Применяем MMR (Maximal Marginal Relevance). Этот алгоритм смотрит на средние векторы и следит, чтобы в финальный результат (top-15) не попали чанки, которые слишком похожи друг на друга.
Что это дает в итоге: Вместо того чтобы получить 15 фрагментов текста, которые все "немножко похожи" на запрос в целом, вы получаете фрагменты, в которых есть конкретные предложения, максимально точно отвечающие на ваши вопросы, причем эти фрагменты будут максимально разнообразными по смыслу.


# Организация векторной базы данных

Вот оптимальная структура организации такой базы:1. Схема хранения (Data Schema)Вместо того чтобы хранить один вектор на одну строку, вы создаете таблицу, где каждая строка — это отдельное предложение, но с общим идентификатором родительского чанка.Vector IDChunk ID (Parent)Sentence VectorSentence TextMetadata (Doc Name, Page, etc.)v_001chunk_A[0.12, -0.05, ...]"За 9 месяцев выпуск вырос на 9%."{ "source": "report.pdf" }v_002chunk_A[0.01, 0.44, ...]"Это обусловлено вводом мощностей."{ "source": "report.pdf" }v_003chunk_B[0.88, 0.11, ...]"Чистая прибыль составила..."{ "source": "report.pdf" }2. Реализация поиска MaxSim на стороне БДЧтобы реализовать ваш алгоритм через базу данных, процесс поиска (Retrieval) делится на три этапа:Vector Search: Вы подаете вектор запроса в БД. БД находит, например, топ-100 ближайших предложений по косинусному сходству во всей базе.Grouping (Max): Вы группируете результаты по Chunk ID. Для каждой группы (чанка) оставляете только то предложение, у которого score (сходство) максимален. Это и есть ваш MaxSim.Parent Retrieval: Из хранилища извлекается полный текст отобранных чанков для дальнейшего ранжирования.3. Организация MMR и АгрегацииПоскольку ваш алгоритм требует вычисления центроиды (среднего вектора) для MMR, вам нужно хранить в метаданных чанка заранее вычисленный средний вектор.Рекомендуемый пайплайн записи в БД:На этапе загрузки: Разбили чанк на предложения -> Векторизовали каждое -> Вычислили средний вектор всех предложений чанка.Сохранение:В «Векторный индекс» записываете все векторы предложений (для поиска).В «Документное хранилище» (или отдельную таблицу метаданных) записываете полный текст чанка и его средний вектор (для этапа MMR).4. Технические рекомендации по выбору инструментовДля вашего специфического подхода (сумма баллов по 5 запросам + MaxSim) лучше всего подойдут:Qdrant: Отлично поддерживает фильтрацию и хранение сложных метаданных. Позволяет делать эффективный поиск с группировкой по полю (group_by="chunk_id"), что автоматически вернет вам лучшие предложения для каждого чанка (MaxSim).Elasticsearch / OpenSearch (с плагином k-NN): Идеально подходят для агрегации баллов. Вы можете выполнить поиск по 5 векторам одновременно и настроить скрипт ранжирования, который суммирует их веса.PGVector (PostgreSQL): Хороший выбор, если вам привычна SQL-структура. Можно легко делать DISTINCT ON (chunk_id) ORDER BY cosine_distance для реализации MaxSim.Резюме: Вам нужно хранить вектора предложений как первичные элементы поиска, но привязывать их к ID чанка, чтобы на лету «схлопывать» результаты поиска до уровня целых блоков текста.

Для того чтобы система не путала данные разных компаний и работала только с нужным контекстом, вам необходимо внедрить метафильтрацию. В векторных базах данных это стандартный механизм, который позволяет ограничить область поиска еще до того, как начнется сравнение векторов.Вот как организовать архитектуру базы данных, чтобы она учитывала эмитента:1. Обогащение метаданных (Metadata Tagging)При сохранении каждого вектора (предложения) в базу, вы добавляете к нему «паспорт» объекта. В вашем случае ключевыми полями будут:issuer_id (ИНН, ОГРН или уникальный тикер эмитента).security_id (ISIN или тикер конкретной бумаги, если данные относятся только к ней).document_type (например, «годовой отчет», «существенный факт», «проспект эмиссии»).2. Двухуровневый процесс поискаВместо поиска по всей базе, ваш алгоритм должен работать в два этапа:Жесткий фильтр (Pre-filtering): Вы передаете в запрос ID конкретного эмитента. База данных мгновенно отсекает все вектора, которые к нему не относятся.Векторный поиск (Similarity Search): Внутри оставшегося подмножества (только данные нужной компании) выполняется ваш алгоритм MaxSim.3. Пример структуры записи в БДВаш объект в векторном хранилище будет выглядеть примерно так:JSON{

Почему это важно для вашего алгоритма?Если не использовать фильтрацию по эмитенту, возникнут следующие проблемы:Галлюцинации: Если вы спросите «какой выпуск продукции?», система может найти «9%» у «Акрона», но если в базе есть отчет условного «Газпрома» с ростом 15%, и его вектор окажется семантически ближе, вы получите неверную цифру.  Нарушение MMR: Алгоритм разнообразия (MMR) может подмешать в топ-15 чанки от разных компаний, если они описывают схожие процессы (например, описание рисков везде похоже).Как это реализовать технически?Большинство современных баз (Qdrant, Pinecone, Milvus) поддерживают фильтрацию на лету. В коде запроса это выглядит как логическое условие:«Найти вектора, максимально похожие на мой запрос, НО ТОЛЬКО ТЕ, где issuer_id == "AKRN"».Это гарантирует, что даже если в базе лежат миллионы предложений от сотен компаний, поиск будет идти в изолированном «песочнице» конкретного эмитента.
