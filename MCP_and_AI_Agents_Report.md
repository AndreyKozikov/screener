# Отчёт: внедрение MCP-сервера и ИИ-агентов в BondsScreener

Дата: 2026-11-12

---

## 1. Обзор архитектуры проекта

Проект состоит из четырёх независимых компонентов:

| Компонент | Технология | Порт | Назначение |
|---|---|---|---|
| `backend` | FastAPI (Python) | 8000 | Основной API: облигации, эмитенты, рейтинги, прогнозы, портфель, макро-дашборд, **ИИ-агент**, LLM-анализ, векторный поиск (RAG) |
| `conversion_service` | FastAPI (Python) | 12345 | Обновление/конвертация данных: e-disclosure, рыночные данные (купоны, валюта, ключевая ставка, рейтинги, RUONIA, история торгов), PDF-конвертация, прогнозы |
| `db_repository` | FastAPI (Python) | 8964 | Хранилище SQLite (4 БД: bonds, blog, history_db, portfolios) + RPC-диспетчер с allowlist |
| `frontend` | React + Vite + TypeScript | 5173 | UI: страницы агента, портфеля, блога, настроек, макро-дашборда |

### Ключевые существующие ИИ-компоненты (важно для оценки)

1. **ИИ-агент подбора облигаций** (`backend/app/agent/`) — уже реализован:
   - `router.py` — эндпоинт `/api/agent/chat`;
   - `service.py` — оркестратор: роутер → инструмент → финализатор;
   - `tools.py` — реестр инструментов `TOOL_HANDLERS` + `TOOL_SCHEMAS` (5 инструментов: `search_bonds`, `get_bond_detail`, `get_key_rate`, `get_coupons`, `bond_rag_query`);
   - `contracts.py` — строгая Pydantic-валидация решений роутера и аргументов инструментов;
   - `llm_client.py` — обёртка над LLM-провайдерами с фолбэком и JSON-repair;
   - `prompts.py`, `rules/`, `skills/` — система правил и навыков (Agent Skills формат);
   - `session.py`, `session_logger.py` — хранение и логирование сессий.

2. **Абстракция LLM-провайдеров** (`backend/app/services/llm/`) — Gemini, OpenAI, OpenRouter, локальный; фабрика `LlmProviderFactory`, реестр, задачи (`floater_task`, `qa_task`, `expand_query_task`).

3. **Векторный поиск / RAG** (`backend/app/services/vector_retrieval/`) — чанкинг, эмбеддинги (dense + sparse, гибрид), ранжирование (MMR), построение контекста.

4. **RPC-диспетчер с allowlist** (`db_repository/services/repository_rpc_service.py`) — `_ALLOWED_OPERATIONS` разрешает только явно перечисленные методы репозиториев; сериализация/десериализация типов.

## 2. Направление 1: внедрение MCP-сервера

### 2.1. Что такое MCP и зачем он здесь

MCP (Model Context Protocol) — открытый протокол, позволяющий внешним ИИ-клиентам (Claude Desktop, Cursor, IDE-ассистенты, другие агенты) обращаться к инструментам и данным приложения через стандартизированный интерфейс (`tools`, `resources`, `prompts`). В отличие от внутреннего агента, MCP открывает функциональность BondsScreener **внешним** потребителям.

### 2.2. Целесообразность

**Высокая.** Проект уже содержит почти всё необходимое для MCP:

- Реестр инструментов `TOOL_HANDLERS`/`TOOL_SCHEMAS` в `backend/app/agent/tools.py` — это, по сути, готовый каталог MCP-инструментов (имя, описание, JSON-схема аргументов, обработчик).
- Слой сервисов (`bonds_service`, `coupon_service`, `keyrate_service`, `llm_analysis_service`, `vector_retrieval_service`) — чистые функции, которые можно обернуть в MCP-инструменты без изменения бизнес-логики.
- Паттерн allowlist в `db_repository` — готовый образец безопасного ограничения набора операций, который следует повторить для MCP.

Основная ценность MCP — **повторное использование** уже написанной логики подбора/анализа облигаций внешними ассистентами без дублирования кода и без привязки к конкретному UI.

### 2.3. Для чего можно внедрить MCP (конкретные инструменты и ресурсы)

**Инструменты (tools):**

| MCP-инструмент | Источник (существующий код) | Назначение |
|---|---|---|
| `search_bonds` | `agent/tools.py::_run_search_bonds` | Подбор облигаций по фильтрам |
| `get_bond_detail` | `agent/tools.py::_run_get_bond_detail` | Детальная информация по SECID/ISIN |
| `get_coupons` | `agent/tools.py::_run_get_coupons` | График купонных выплат |
| `get_key_rate` | `agent/tools.py::_run_get_key_rate` | Ключевая ставка ЦБ РФ |
| `bond_rag_query` | `agent/tools.py::_run_bond_rag_query` | Ответ по документам/событиям облигации (RAG) |
| `get_ratings` | `db_repository` (bond_ratings) | Рейтинги эмитента/выпуска |
| `get_forecast` | `forecast_service` | Прогнозы (ключевая ставка, инфляция) |
| `get_inflation` | `inflations` | Данные по инфляции |
| `get_ruonia` | `ruonia_service` | Ставка RUONIA |
| `get_portfolio` | `portfolio` | Позиции портфеля пользователя |
| `get_emitent` | `emitent_service` | Данные эмитента |

**Ресурсы (resources):**

| MCP-ресурс | Назначение |
|---|---|
| `bonds://metadata` | Справочник полей/колонок облигаций |
| `bonds://filter-options` | Допустимые значения фильтров |
| `portfolio://{user_id}` | Снимок портфеля |
| `docs://{secid}` | Markdown-документы эмиссии (для RAG) |

**Промпты (prompts):** шаблоны «подбери облигации», «проанализируй портфель», «объясни прогноз» — переиспользуют существующие `rules/` и `skills/`.

### 2.4. Что потребуется создать вновь

1. **MCP-сервер** (новый микросервис или встроенный модуль). Рекомендуется отдельный лёгкий сервис `mcp_server/` на Python с SDK `mcp` (FastMCP), чтобы не нагружать `backend` и изолировать транспорт. Альтернатива — встроить в `backend` как дополнительный ASGI-эндпоинт (SSE/streamable HTTP).

2. **Адаптеры инструментов** — тонкие обёртки, которые:
   - берут схемы из `TOOL_SCHEMAS`/`tool_args_schema()` (уже есть);
   - вызывают существующие сервисы (уже есть);
   - приводят результат к MCP-формату (текст/структурированный контент).

3. **Провайдеры ресурсов** — функции чтения справочников/портфеля/документов.

4. **Конфигурация и аутентификация** — отдельный API-ключ для MCP (по образцу `DB_REPOSITORY_API_KEY`), настройки в `config.toml`/`.env`.

5. **Деплой-артефакты** — `run_mcp_service.py`, systemd-юнит, `DEPLOYMENT.md` (по образцу `db_repository`).

### 2.5. Что придётся изменить

1. **Вынести реестр инструментов в общий модуль.** Сейчас `TOOL_HANDLERS`/`TOOL_SCHEMAS` живут внутри `app/agent/tools.py` и завязаны на `ToolOutput`/`AgentSource`. Для переиспользования MCP и агентом их стоит выделить в транспорт-независимый слой (например, `app/tools/`), а `agent/tools.py` оставить как адаптер.

2. **Сделать сервисы транспорт-независимыми.** Часть сервисов синхронные и вызываются через `asyncio.to_thread`; для MCP это допустимо, но стоит унифицировать интерфейс вызова (async-обёртки).

3. **Аутентификация.** Добавить проверку MCP-ключа (по образцу `db_repository/core/security.py::require_api_key`).

4. **Разграничение доступа.** Для портфеля/персональных данных нужен контекст пользователя (OAuth/токен), а не только сервисный ключ — иначе MCP не сможет безопасно отдавать персональные данные.

5. **Документация и конфигурация** — описать инструменты в `config.toml`, добавить флаг включения (по образцу `AGENT_ENABLED`).

### 2.6. Риски и ограничения

- **Безопасность:** MCP открывает данные наружу; обязателен allowlist инструментов (как `_ALLOWED_OPERATIONS`) и аутентификация.
- **Персональные данные:** портфель требует пользовательской авторизации, а не только сервисного ключа.
- **Стоимость/латентность:** `bond_rag_query` дорогой и медленный — для MCP стоит ограничить/кэшировать.
- **Версионирование схем:** JSON-схемы инструментов должны быть стабильными, чтобы не ломать внешних клиентов.

## 3. Направление 2: внедрение ИИ-агентов

### 3.1. Текущее состояние

Уже реализован **один агент** — подбор облигаций (`backend/app/agent/`), с архитектурой «роутер → инструмент → финализатор», системой правил (`rules/`) и навыков (`skills/`), строгой валидацией контрактов и логированием сессий. Это зрелая основа для расширения.

### 3.2. Для каких частей можно внедрить агентов

| # | Агент | Где внедрить | Функции | Зачем |
|---|---|---|---|---|
| 1 | **Агент подбора облигаций** (существует) | `backend/app/agent/` | Подбор по фильтрам, детали, купоны, ставка, RAG | Основной сценарий пользователя |
| 2 | **Агент анализа портфеля** | `backend` + `portfolio` | Оценка состава, дюрация, риск, предложения по ребалансировке, сравнение с бенчмарком | Повышение ценности для инвестора |
| 3 | **Агент анализа документов/событий** (частично есть как `bond_rag_query`) | `backend` + `vector_retrieval` | Глубокий разбор эмиссионных документов, оферт, формул купона, событий раскрытия | Автоматизация чтения проспектов |
| 4 | **Агент макро/прогнозов** | `backend` + `forecast`/`inflations`/`keyrate`/`ruonia` | Объяснение прогнозов ставки/инфляции, сценарии, влияние на облигации | Аналитическая поддержка |
| 5 | **Агент мониторинга данных** | `conversion_service` | Контроль свежести данных, обнаружение аномалий, авто-запуск обновлений, отчёты | Снижение ручной работы по обновлению |
| 6 | **Агент поддержки/онбординга** | `frontend` + `backend` | Объяснение интерфейса, фильтров, терминов, помощь новым пользователям | Снижение нагрузки на поддержку |

### 3.3. Функции и обоснование по каждому агенту

**Агент анализа портфеля (приоритет высокий).** Данные портфеля уже есть (`portfolio`, `portfolio_reports`, `get_current_positions_for_user`). Агент должен: агрегировать позиции, считать дюрацию/доходность портфеля, выявлять концентрацию по эмитентам/секторам, давать рекомендации. Зачем: это естественное продолжение существующего агента и главный запрос инвестора.

**Агент анализа документов.** Уже есть RAG-пайплайн и инструмент `bond_rag_query`. Расширение: многошаговый анализ (несколько вопросов по одному документу), сравнение выпусков, извлечение структурированных параметров (формула купона, оферты) — частично покрыто `floater_task`. Зачем: убрать ручной разбор проспектов.

**Агент макро/прогнозов.** Данные прогнозов/инфляции/ставки уже есть. Агент объясняет прогнозы и их влияние на доходности. Зачем: превратить сырые данные в понятные выводы.

**Агент мониторинга данных.** `conversion_service` содержит сервисы обновления (`*_update_service`). Агент может планировать/запускать обновления, проверять свежесть, сообщать об ошибках. Зачем: автоматизация эксплуатации.

**Агент поддержки.** Объяснение возможностей и ограничений (уже частично в `rules/router.md` через `intent=answer`). Зачем: онбординг.

### 3.4. Что потребуется разработать вновь

1. **Оркестрацию нескольких агентов.** Сейчас один `AgentService`. Нужен диспетчер/роутер верхнего уровня, который направляет запрос нужному агенту (или композиция агентов). Можно расширить существующий роутер новыми `intent`/инструментами, либо ввести отдельные агенты с общим диспетчером.

2. **Новые инструменты** в `TOOL_HANDLERS`/`TOOL_SCHEMAS`:
   - `get_portfolio`, `analyze_portfolio` (портфель);
   - `get_forecast`, `get_inflation`, `get_ruonia` (макро);
   - `get_ratings`, `get_emitent` (справочные);
   - `run_data_update`, `check_data_freshness` (мониторинг).

3. **Новые правила и навыки** (`rules/`, `skills/`) для каждого агента — по образцу существующих `rating-filter-selection`, `bond-kind-selection`, `yield-filter-selection`.

4. **Память/контекст агента.** Сейчас есть `session.py` (история диалога). Для портфельного агента нужен персистентный контекст пользователя (позиции, предпочтения).

5. **Оценка качества (eval).** Набор тестовых сценариев и метрик для проверки агентов (точность маршрутизации, корректность фильтров, отсутствие галлюцинаций).

6. **Планировщик для агента мониторинга** — cron/фоновые задачи (в проекте нет готового планировщика; можно использовать `schedule`/Celery или внешний cron).

### 3.5. Что придётся изменить

1. **`contracts.py`** — расширить `TOOL_ARG_MODELS`, `ROUTER_DECISION` (новые инструменты и, возможно, новые `intent`).

2. **`tools.py`** — добавить обработчики и схемы новых инструментов.

3. **`prompts.py` / `rules/`** — расширить системный промпт роутера и правила маршрутизации.

4. **`service.py`** — поддержать многошаговость (сейчас «ровно один вызов инструмента за ход»), если нужны цепочки (например, «найти бумаги → изучить документы»).

5. **`main.py` / `settings.py`** — регистрация новых роутеров, флаги включения (по образцу `AGENT_ENABLED`).

6. **`frontend`** — расширить `AgentChatPage.tsx`/`api/agent.ts` под новые типы ответов (портфель, прогнозы, графики).

7. **`conversion_service`** — для агента мониторинга добавить эндпоинты запуска/статуса обновлений (частично есть).

### 3.6. Риски и ограничения

- **Галлюцинации** — уже частично решено строгими контрактами и правилом «факты только из инструментов»; нужно распространить на новые агенты.
- **Стоимость LLM** — многошаговые агенты и RAG дороги; нужны лимиты и кэширование.
- **Безопасность персональных данных** — портфельный агент требует авторизации.
- **Сложность оркестрации** — несколько агентов усложняют тестирование и отладку.

## 5. Сравнительная таблица: ИИ-агенты vs MCP

| Критерий | ИИ-агенты | MCP-сервер |
|---|---|---|
| **Суть** | Автономная логика: понимает запрос, выбирает инструменты, формирует ответ | Протокол/интерфейс: стандартизированно отдаёт инструменты и данные внешним клиентам |
| **Кто потребитель** | Конечный пользователь приложения (через чат в UI) | Внешние ИИ-клиенты (Claude Desktop, Cursor, IDE, другие агенты) |
| **Где живёт логика** | Внутри `backend` (роутер, финализатор, правила) | Тонкий слой поверх существующих сервисов |
| **Принимает ли решения** | Да: маршрутизация, уточнения, финализация ответа | Нет: только предоставляет инструменты; решение принимает внешний клиент |
| **Нужен ли LLM внутри** | Да (роутер + финализатор) | Нет (MCP сам по себе не вызывает LLM) |
| **Сложность внедрения** | Выше (оркестрация, промпты, eval, анти-галлюцинации) | Ниже (обёртки над готовыми сервисами) |
| **Что переиспользует** | Сервисы, RAG, LLM-провайдеры, сессии | Те же сервисы + реестр инструментов агента |
| **Безопасность** | Внутренняя авторизация приложения | Отдельный API-ключ + allowlist; персональные данные требуют OAuth |
| **Ценность для бизнеса** | Прямая: готовые ответы и рекомендации пользователю | Косвенная: расширяемость, интеграция с внешними ассистентами |
| **Зависимость от UI** | Связан с фронтендом (`AgentChatPage`) | Независим от UI |
| **Пример в проекте** | `backend/app/agent/` (подбор облигаций) | Пока отсутствует; прототип — `TOOL_HANDLERS` + `_ALLOWED_OPERATIONS` |

**Ключевое различие:** агент — это «мозг» (сам решает, что делать), MCP — это «руки» (стандартный способ дать внешнему мозгу доступ к функциям). Они не конкурируют: MCP может отдавать наружу те же инструменты, которые использует внутренний агент, а внутренний агент может в будущем сам выступать MCP-клиентом для других систем.

## 6. Рекомендуемая последовательность внедрения

1. **Вынести реестр инструментов** в общий модуль (`app/tools/`) — это разблокирует и MCP, и новых агентов.
2. **MCP-сервер (MVP)** — обернуть 5 существующих инструментов агента + справочники; аутентификация по ключу.
3. **Агент анализа портфеля** — новые инструменты `get_portfolio`/`analyze_portfolio`, правила, фронтенд.
4. **Агент макро/прогнозов** — инструменты `get_forecast`/`get_inflation`/`get_ruonia`.
5. **Агент мониторинга данных** — планировщик + эндпоинты в `conversion_service`.
6. **Eval-инфраструктура** — тестовые сценарии и метрики для всех агентов.
