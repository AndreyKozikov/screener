# Событийный индекс облигаций

Микросервис получает события и поисковые запросы через HTTP API. Для обоих POST-запросов клиент передаёт заголовки `Content-Type: application/json` и `X-API-Key`.

## Наполнение базы

Внешняя система вызывает `POST /index/events` и передаёт полный каталог выпусков одного эмитента и пакет событий в теле запроса.

```json
{
  "inn": "5504036333",
  "bonds": [{"secid":"SEC123","isin":"ISIN123","secname":"Эмитент БО-19","issuename":"Биржевые облигации серии БО-19","reg_number":"REG123","first_tradedate":"2024-01-01"}],
  "events": [{"inn":"5504036333","event_key":"example-event","pseudo_guid":"example-guid","source_index":0,"event_name":"Ставка купона","event_date":"2025-05-05","full_text":"По выпуску SEC123 установлена ставка купона 14%.","is_corrected_by_another_event":false}]
}
```

В карточке выпуска обязательны `secid` и `isin`. Серия извлекается из `secname` и `issuename`; если из `secname` серия не извлечена, используется серия из `issuename`. Если серии различаются без учёта регистра, сопоставление с текстом идёт по обеим. Реквизиты каждого выпуска для сопоставления берутся из массива `bonds` этого запроса.

1. Роутер получает проверенную Pydantic-модель запроса. Ошибка формата, например отсутствующее обязательное поле или некорректная дата, возвращает HTTP 400 до записи.
2. Сервис отмечает выпуски эмитента как обработанные и проверяет полный исходный текст каждого события по каждому выпуску. Приоритет совпадения — SECID, регистрационный номер, полное наименование выпуска из `issuename`, затем серия. Наименование ищется без учёта регистра, с допуском на пробелы и переносы строк; серия проверяется по значениям из `secname` и `issuename`.
3. Для события с совпадениями сервис очищает текст и создаёт один чанк с названием события, датой и описанием. Для каждого предложения чанка модель BGE-M3 вычисляет плотный вектор и лексические веса.
4. Репозиторий проверяет записи по моделям таблиц и записывает предложения, чанк и связи со всеми совпавшими выпусками. После проверки записи версия события становится активной. При повторной отправке укажите тот же `event_key` и полный каталог выпусков эмитента. События фиксируются по отдельности.

Для приведённого запроса успешный ответ HTTP 200 выглядит так:

```json
{"indexed":1,"skipped_invalid":0,"skipped_no_match":0,"skipped_inn_mismatch":0}
```

`indexed` считает записанные события. Остальные счётчики показывают число пропусков из-за пустого текста, отсутствия совпадения с выпусками и несовпадения ИНН события с ИНН запроса соответственно.

## Хранение в LanceDB

| Таблица | Что содержит одна запись |
|---|---|
| `bond_event_map` | Связь версии события с выпуском, реквизиты бумаги, включая `issuename`, и причину совпадения. |
| `event_chunks` | Чанк одной версии события с очищенным текстом и метаданными. |
| `event_vectors` | Одно предложение чанка, его позицию, плотный вектор и лексические веса. |
| `event_state` | Статус события и указатель на его активную версию. |
| `bond_index_state` | SECID обработанного выпуска и время отметки, в том числе для выпуска без совпадений. |
| `index_meta` | Параметры модели и индекса, идентификатор конфигурации и номер изменения каталога. |

Если текст относится к двум выпускам, репозиторий сохраняет две связи с одним чанком. Оба выпуска используют одни и те же векторы предложений.

## Поиск

Клиент вызывает `POST /search` и передаёт идентификатор выпуска и вопросы в теле запроса.

```json
{"bond":{"secid":"SEC123"},"queries":["Какова ставка купона?"],"provider":"local"}
```

Ответ содержит статус, идентификаторы снимка и индекса, ранжированные события с оценками и готовый Markdown-контекст. Для известной бумаги без подходящих событий возвращается пустой результат, для необработанной — статус `not_indexed`.

Для поиска укажите SECID или ISIN и хотя бы один непустой вопрос. Сервис отбирает активные версии событий выпуска и возвращает до 30 результатов. HTTP 202 означает `not_indexed`, HTTP 401 — ошибку ключа доступа, HTTP 409 — несовместимость запрошенного провайдера с локальным индексом. Схемы запросов и ответов доступны в `/docs` работающего сервиса.

## Структура микросервиса

| Слой | Ответственность |
|---|---|
| [routers/](routers/) | Приём HTTP-запросов, проверка доступа и формирование HTTP-ответов. |
| [models/api.py](models/api.py) | Pydantic-модели запросов и ответов для записи и поиска. |
| [services/document_index.py](services/document_index.py) | Сопоставление событий, подготовка чанков, векторизация и ранжирование. |
| [repository/vector_store.py](repository/vector_store.py) | Чтение и запись LanceDB, фиксация активных версий, снимки для поиска и очистка. |
| [models/records.py](models/records.py) и [schema.py](schema.py) | Pydantic-модели строк шести таблиц и физические типы колонок PyArrow. |
| [config/settings.py](config/settings.py) | Загрузка и проверка настроек сервиса. |

## Запуск сервера

Несекретные настройки собраны в `config/config.toml` (пример — `config/config.example.toml`). Переменные окружения имеют приоритет над `.env` и TOML. Ключ API задаётся через окружение или `.env`.

Установите зависимости из `vector_service/requirements.txt`. Задайте `VECTOR_SERVICE_API_KEY` и `VECTOR_MODEL_DIR` с путём к локальной модели BAAI/bge-m3 с токенизатором, весами энкодера и файлами `sparse_linear.pt` и `colbert_linear.pt`. При необходимости задайте каталог базы в `VECTOR_DB_DIR`.

```powershell
python -m uvicorn vector_service.main:app --host 127.0.0.1 --port 8100 --workers 1
```

Состояние сервера доступно через `GET /health`, готовность поиска — через `GET /ready`.
