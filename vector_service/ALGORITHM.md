# Алгоритм работы микросервиса

## Задача 1. Наполнение базы данных новыми событиями

### 1.1. Получение запроса на индексацию

Внешняя система отправляет пакет одного эмитента в теле HTTP-запроса `POST /index/events`. Микросервис обрабатывает пакет последовательно и фиксирует каждое событие отдельно.

В рамках одного пакета каталог бумаг (1.3) строится один раз, шаги 1.4–1.8 выполняются для каждого события последовательно, завершение (1.9) — после обработки всех событий.

**Каталог индекса** — это папка на диске, в которой LanceDB хранит все таблицы индекса: связи бумаг и событий, чанки событий, векторы предложений, состояние событий, список проиндексированных бумаг и метаданные индекса. Если папки ещё нет, она создаётся; если индекс уже построен, открывается существующий.

При старте HTTP-сервера открывается каталог индекса. Путь к каталогу индекса задаётся настройками сервиса при запуске сервера.

### 1.2. Источники данных

- **Пакет событий** — набор данных, который формирует вызывающая система вне микросервиса. В нём уже собраны ИНН эмитента, каталог его бумаг и события. Пакет приходит готовым в теле HTTP-запроса `POST /index/events`.
- **Реквизиты бумаг** — берутся из каталога бумаг внутри пакета: SECID, ISIN, регистрационный номер, название, наименование выпуска и дата начала торгов.
- **События** — берутся из того же пакета: ключ события, псевдо-GUID, порядковый номер в источнике, тип события, дата, полный исходный текст, признак корректировки другим событием, ИНН эмитента.
- **База данных** — таблицы LanceDB, расположенные в каталоге индекса.

Микросервис не читает первоисточники раскрытия информации и не обращается к базе данных приложения: он получает уже подготовленный пакет от вызывающей системы.

### 1.3. Построение каталога бумаг эмитента

Из пакета берётся полный каталог бумаг эмитента. По каждой бумаге формируется карточка: SECID, ISIN, регистрационный номер, название, наименование выпуска, серия и дата начала торгов.

Наименование выпуска (`issuename`) сохраняется как отдельный реквизит бумаги и участвует в сопоставлении с текстом события. Серия отдельным полем не приходит — она извлекается из названия бумаги (`secname`) и из наименования выпуска (`issuename`) по набору маркеров («серия», «серии», «об.сер.», «БО», «обл.», «сер.», варианты с дефисом и датой в конце названия) с приоритетом маркеров. Если маркеров нет, серия берётся из последнего слова названия перед служебным окончанием. Кавычки и знаки препинания вокруг значения серии отбрасываются.

В карточку бумаги записывается серия из `secname`, а если её извлечь не удалось — серия из `issuename`. Для сопоставления с текстом сохраняются обе серии: если они совпадают без учёта регистра, используется одна, иначе — обе.

Каталог фиксируется в базе как список бумаг эмитента, для которых строился индекс.

### 1.4. Связывание событий с бумагами

Связывание выполняется по полному исходному тексту события — до очистки текста.

Для каждого события проверяется каждая бумага каталога, и фиксируется первая сработавшая причина в порядке приоритета:

1. **SECID** — идентификатор бумаги найден в тексте как отдельное слово без учёта регистра.
2. **Регистрационный номер** — номер найден в тексте целиком, с нормализацией визуально похожих кириллических и латинских символов.
3. **Наименование выпуска** — полная фраза из `issuename` встречается в тексте без учёта регистра; между словами допускаются пробелы и переносы строк, а границы фразы проверяются по целым словам.
4. **Серия** — любая из серий бумаги (из `secname` и из `issuename`) найдена в тексте без учёта регистра, с допуском на варианты дефиса и пробелы вокруг него.

Событие связывается со всеми бумагами, для которых сработала хотя бы одна причина. Одно событие может относиться сразу к нескольким бумагам эмитента. Для каждой пары «бумага — событие» сохраняется причина связи: `secid`, `reg_number`, `series` или `issuename`. Если у бумаги сработало несколько причин, фиксируется старшая по приоритету.

### 1.5. Очистка текста

Из текста события удаляются служебные фрагменты раскрытия: блок «Общие сведения» до начала «Содержания сообщения», блок подписи, нумерация пунктов и служебный заголовок «Содержание сообщения». Остаётся содержательная часть сообщения, и именно она попадает в чанк.

### 1.6. Чанкование

Действует правило «одно событие — один чанк». Текст чанка состоит из трёх частей:

- тип события;
- дата события;
- очищенное описание события.

Чанк получает служебные признаки: тип источника «событие», идентификатор источника вида «событие + дата» и раздел, равный типу события.

Текст чанка делится на предложения по знакам конца предложения (точка, восклицательный или вопросительный знак) с последующим пробелом. Каждое предложение становится отдельной единицей векторизации. Если текст не делится, чанк векторизуется как одно предложение.

Итоговая структура: событие → один чанк → несколько предложений.

### 1.7. Векторизация

Для каждого предложения вычисляются два представления:

- **плотный вектор** — смысловое представление предложения фиксированной размерности (1024);
- **разреженные лексические веса** — представление по отдельным словам, используемое для точного совпадения слов, чисел, номеров и терминов.

Векторы считаются на этапе индексации и сохраняются в базе. При поиске они уже не пересчитываются — заново векторизуются только поисковые запросы.

### 1.8. Запись в базу данных

Повторно поданный ключ события создаёт новую версию события. Идентификатор события стабилен и зависит только от ключа события, а идентификатор версии создаётся заново при каждом поступлении. Вместе они образуют уникальный ключ версии.

Запись версии выполняется в такой последовательности:

1. добавляются векторы по предложениям;
2. добавляется чанк события с текстом, типом и датой;
3. добавляются связи события с каждой подходящей бумагой;
4. в состоянии события фиксируется новая активная версия.

Именно фиксация активной версии публикует событие для поиска. В поиске участвует только активная версия; прежние версии остаются в базе до очистки.

Каждое событие пакета проходит эту последовательность и публикуется отдельно от остальных событий пакета.

В результате записи в базе образуются связанные записи:

- **вектор предложения** — ключ версии чанка, идентификатор события, ключ события, идентификатор версии, порядковый номер предложения, текст предложения, плотный вектор и лексические веса;
- **чанк события** — уникальный ключ версии (ключ события + версия), текст чанка, тип и дата события;
- **связь бумаги и события** — SECID, ISIN, регистрационный номер, серия, дата начала торгов и наименование выпуска, ключ и версия события, ключ чанка, дата и год события, порядковый номер в источнике, признак корректировки и причина связи;
- **состояние события** — какая версия события активна;
- **список проиндексированных бумаг** — какие бумаги эмитента уже обрабатывались;
- **метаданные индекса** — конфигурация и отпечаток индекса.

Связь между сущностями:

```
Бумага (SECID / ISIN)
    → связь бумаги и события
        → ключ события + версия
            → чанк события (текст, тип, дата)
            → векторы предложений (плотный вектор + лексические веса)
```

По любому вектору однозначно определяется событие и его версия, а по событию — все бумаги, к которым оно относится. Одно событие может быть связано с несколькими бумагами: в таблице связей для него будет несколько записей с разными SECID/ISIN, но с одним ключом события.

### 1.9. Завершение индексации

После обработки всех событий пакета неактивные версии удаляются из базы, выполняется оптимизация таблиц. В ответ возвращается статистика: сколько событий проиндексировано и сколько отброшено по причинам.

Так как каждое событие публикуется отдельно, повторная отправка пакета обрабатывает уже записанные события как новые версии.

## Задача 2. Запросы к базе данных

### 2.1. Получение запроса

Запрос на поиск поступает по HTTP через `POST /search`. HTTP-процесс одновременно принимает новые записи по `POST /index/events` и обслуживает поиск по уже записанным данным. Запрос поиска сам индекс не изменяет.

Запрос содержит:

- **бумагу** — обязательно SECID или ISIN; дополнительно можно уточнить регистрационный номер и серию;
- **список текстовых запросов**;
- необязательные параметры: дата начала поиска, идентификатор запроса и провайдер векторизации.

### 2.2. Определение событий бумаги

По SECID или ISIN в таблице связей находятся все связи этой бумаги с событиями. Из найденных связей берутся только записи с активной версией события.

### 2.3. Временной фильтр

Нижняя граница берётся из даты начала поиска, если она передана, иначе — из даты начала торгов бумаги. Из этой даты вычисляется набор допустимых годов: с года границы минус один (чтобы захватить регистрацию и размещение) до текущего года включительно. События, чей год не входит в набор, отбрасываются.

### 2.4. Фильтр по реквизитам бумаги

Если в запросе переданы регистрационный номер, серия или ISIN, события дополнительно фильтруются по точному совпадению этих реквизитов с реквизитами бумаги в связи.

### 2.5. Подготовка событий

По отобранным связям поднимаются чанки событий и все векторы их предложений. Для каждого события собираются текст чанка, тип события, дата, идентификатор источника, признак корректировки и вектор каждого предложения с его номером и лексическими весами.

### 2.6. Векторизация запросов

Каждый текстовый запрос векторизуется тем же способом, что и события: получаются плотный вектор запроса и его лексические веса.

### 2.7. Гибридная оценка

Для каждого события и каждого запроса оценка считается на уровне предложений:

- **смысловое сходство** — косинусное сходство плотного вектора запроса и плотного вектора предложения;
- **лексическое сходство** — скалярное произведение разреженных весов запроса и предложения, то есть совпадение конкретных слов и термов;
- **гибридная оценка предложения** — взвешенная сумма смыслового и лексического сходства: вес смысловой составляющей 0,8, лексической 0,2;
- **оценка события по одному запросу** — максимум гибридной оценки по всем предложениям события;
- **итоговая оценка события** — сумма таких максимумов по всем запросам.

События сортируются по убыванию оценки; для дальнейшей обработки отбирается не более 30 лучших.

### 2.8. Переранжирование

Отобранные события дополнительно переранжируются эвристиками, повышающими позицию более информативных и более свежих событий:

- наличие цифр;
- наличие процентов или слова «процент»;
- наличие формул с числами;
- большая длина текста;
- свежесть события: чем ближе дата к текущей, тем больше бонус; бонус плавно затухает со временем, с полупериодом около трёх лет.

Итоговый список сортируется по оценке с учётом эвристик.

### 2.9. Формирование ответа

Ответ содержит:

- статус «ok» или «not_indexed»;
- идентификаторы запроса, снимка и отпечатка индекса;
- SECID и ISIN найденной бумаги;
- время выполнения;
- ранжированный список событий: идентификатор чанка, ключ события, тип события, дата события, идентификатор источника, текст события, признак корректировки и оценка;
- готовый Markdown-контекст для языковой модели: раздел событий, внутри — идентификатор, заголовок и текст каждого события в порядке ранжирования.

Для бумаги без подходящих событий возвращается пустой список результатов и статус «ok». Для бумаги, отсутствующей в индексе, возвращается статус «not_indexed».
